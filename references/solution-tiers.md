# 选型访谈与迁移场景（migration scenarios）

> 执行本技能的第一步必读。访谈规则（三问 / 保守假设 / 理由要求）的**唯一权威**见
> agent-skills-index 的 `conventions/solution-interview.md`；本文只保留本技能的场景矩阵（A/B/C/D）。
> 技术选型第二层访谈见 agent-skills-index 的 `conventions/stack-interview.md`。

## 1. 访谈（一次问清，≤3 问）

| # | 问题 | 取值（示例） | 用途 |
| --- | --- | --- | --- |
| 1 | **目的** | 换服务器 / 灾难恢复 / 日常可重建 / 多机管理 | 场景主轴 |
| 2 | **规模** | 服务数、数据量（GB 级）、是否多机、停机容忍度 | 场景落点 |
| 3 | **硬约束** | 域名与 DNS API、密钥来源、预算、合规 | 修正方案 |

未回答的项按最保守假设处理并在计划中标注"未确认"（规则见 `conventions/solution-interview.md`）。

## 2. 场景矩阵

| 场景 | 目的 | 规模/前提 | 方案要点 | 理由 |
| --- | --- | --- | --- | --- |
| A 整机迁移 | 换服务商/升级 | 多服务，尽量不停机 | B 全流程 + 并行同步 + 双机切换 | 数据量大、服务多，切换窗口要短 |
| B 快速重建 | 旧机不保留 | 单/少服务，可停维护窗口 | GitHub 拉代码 + 数据导入 + 健康检查 | 最简；服务器变成可替换资产 |
| C 灾难恢复 | 旧机失联 | 随时可能发生 | 备份有效性是第一前提 | 平时备份好，出事才能恢复 |
| D 多机统一管理 | 多项目多机 | 项目与机器都多 | 每项目一个"部署清单"，任意机可按清单部署 | 按清单部署，机器不再绑定项目 |

**默认推荐 B+C 架构**：B 让"换机"变成日常动作，C 保证意外发生时有底；A 是 B 的完整版，D 是 B 的批量化。
无论选哪个场景，**Plan（只读扫描）→ 用户确认 → Apply（备份→部署→验证→切换）** 的两阶段流程不变。

## 3. 换场景触发器

- 服务数 ≥3 且彼此有依赖 → 从 B 升 A（需要依赖顺序与统一切换）；
- 出现过一次"旧机失联无法恢复" → 立即补 C（先建备份与恢复演练）；
- 出现第二台机器 → 评估 D（部署清单化）；
- 数据量 >100GB → 数据同步策略从"备份导入"升级为"并行同步 + 切换前增量"。

## 4. 理由模板（写进迁移计划报告）

```text
场景：B（快速重建）
依据：目的=换服务商；规模=3 个 compose 服务，Postgres+Redis；停机容忍 ≤1 小时
理由：服务少、无跨服务强依赖；代码已在 GitHub，compose 完整
为什么不是 A：没有"尽量不停机"的硬要求
为什么不是 C：旧机当前可用，属主动换机而非故障
未确认假设：密钥来源未说明，按"服务器端 600 权限 .env 文件"处理
```
