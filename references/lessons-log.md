## 架构

### L-001 服务器是"可重建资产"：代码、配置、数据三者分开
- 日期：2026-10-15｜来源：设计推理（GitHub+Docker 迁移架构）｜场景：B/C/D
- 结论：迁移不是"把旧机文件系统搬过去"，而是"新机从 GitHub 拉代码、按 compose 重建、只导数据"；服务器随时可换，机器本身不再值钱。
- 为什么＋落地：三层分离后，换机=重建+导数据；灾难恢复=备份有效性。已落 SKILL.md 核心立场 + 四层文档结构。

### L-002 活库目录打包 = 数据损坏：数据库只走原生一致性备份
- 日期：2026-10-15｜来源：设计推理（数据库一致性）｜场景：全部
- 结论：运行中的数据库文件随时在写，直接复制容器目录大概率得到损坏快照；必须用 `pg_dump/mysqldump/BGSAVE` 等一致性工具，并**恢复演练**验证备份可打开。
- 为什么＋落地：备份打不开 = 没有备份。已落 data-migration.md 红线 + 检查表。

### L-003 容器 Up ≠ 网站可用：健康检查是迁移完成的唯一标准
- 日期：2026-10-15｜来源：设计推理（运维常识制度化）｜场景：全部
- 结论：compose 起来只说明进程在跑；还要验 HTTP 2xx/3xx、数据库连接与数据量、关键 API、后台任务、日志无错误。
- 为什么＋落地：把"健康检查门槛"写进不可妥协项，五条全过才算迁移完成（migration-playbook.md §2）。

### L-004 DNS 切换要有 TTL 与回滚窗口：证书优先重签
- 日期：2026-10-15｜来源：设计推理｜场景：A/B/C
- 结论：切换前把 TTL 降到 300 并等旧值过期；旧机保留 72h 可回切；HTTPS 证书在新机重签（ACME），不迁移私钥。
- 为什么＋落地：没有回滚窗口的 DNS 切换是"一锤子买卖"；私钥跨机传输扩大暴露面。已落不可妥协项 5/6。

### L-005 密钥的唯一原则：不进仓库、不进镜像、安全通道注入
- 日期：2026-10-15｜来源：设计推理（对齐 MSP 凭据纪律）｜场景：全部
- 结论：仓库只放 `.env.example`（列 key 名）；真实密钥经安全通道落到新机 `/srv/secrets`（600），部署时注入，绝不在日志/镜像层出现。
- 为什么＋落地：一次误提交 = 全部轮换。已落不可妥协项 3 + infrastructure.md 目录规划。
